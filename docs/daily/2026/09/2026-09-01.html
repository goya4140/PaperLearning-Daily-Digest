HiRS-Agent: A Hierarchical Multi-Agent System for Reliable Long-Horizon Remote Sensing Task Solving

Boyang Mu, Zhiwei Wei, Mugen Peng, Wenjia Xu

HiRS-Agent：面向可靠长周期遥感任务的分层多智能体系统

入选理由：分层多智能体架构解决遥感长周期任务，强化工具链可靠性

查看 arXiv 摘要

Recent advances in large language models and multimodal models have pushed remote sensing (RS) processing from simple perception models to agentic systems designed to tackle complex, long-horizon RS tasks. However, existing systems often rely on monolithic decision-making frameworks, which fail to accommodate the multi-stage, interdependent nature of RS tasks. This centralized approach leads to challenges such as unstable task execution, incorrect tool usage, and error propagation across stages. To address these issues, we propose HiRS-Agent, a hierarchical multi-agent system for long-horizon RS task solving. HiRS-Agent adopts a two-level collaborative architecture: the Manager Layer handles dynamic routing, step-level verification, replanning, and termination control, while the Specialist Layer organizes domain-specific tools according to the RS workflow and is responsible for subtask reasoning and tool execution. To further enhance the system's capability, we introduce a two-stage supervised tuning strategy and a verification-guided hierarchical reinforcement learning stage to jointly optimize coordination and tool-use policies. Experiments on Earth-Agent Benchmark and ThinkGeo show that HiRS-Agent substantially improves long-horizon tool-use capability and final-task correctness, demonstrating the effectiveness of structured multi-agent collaboration for reliable RS agents. The code is publicly available at https://github.com/IntelliSensing/HiRS-Agent.

One Policy Is Enough: Single-Agent Reinforcement Learning Outperforms Tree Search for Chemistry Tool Learning

Armin Dariani, Sifan Wu, Bang Liu, Entao Yang

单策略胜过树搜索：化学工具学习新范式

入选理由：单策略端到端生成替代树搜索，显著提升化学工具调用精度

查看 arXiv 摘要

Chemistry questions often demand exact computation and database lookups that a language model cannot supply from its parameters, so it must reach for external tools. Tool use here is a three-part problem: select the right tool from a large pool, fill it with correctly typed arguments, and chain calls so that each consumes the outputs of the last. CheMatAgent, a previously published system, addresses this with hierarchical evolutionary MCTS: separate policy and execution models searching tool-call trees under two learned critics, one regressed partly onto GPT-assigned scores. We show that a single policy suffices. Our model interleaves reasoning, tool calls, and returns in one left-to-right generation, trained by a supervised warm-up and then outcome-level reinforcement learning against a programmatic reward read directly off the gold call chain, which leaves no learned critic and no judge in the training loop. On ChemToolBench multiple-tool comprehensive chemistry, on both backbones CheMatAgent use, we improve Tool F1 by 5.5% and Return F1 by 9.6% on Qwen-2.5-7B, and by 3.7% and 3.9% on Llama-3.1-8B, compared with their strongest search configuration, at one model invocation per question, against a search whose cost grows with the tree; we also lead answer Pass Rate on Qwen-2.5-7B.

Large language models (LLMs) offer promising clinical decision support but remain vulnerable to hallucinated facts, unsupported recommendations, and citation errors. We present DIASENTINEL, a fully on-premise multi-agent system for one-year type 2 diabetes mellitus (T2DM) risk screening and guideline-grounded report generation from electronic health records (EHRs). The system integrates calibrated risk prediction, deterministic clinical signal extraction, Reciprocal Rank Fusion over American Diabetes Association (ADA) guidelines, and a hybrid verification layer combining rule-based checks with LLM entailment. The demonstration provides a real-time batch-screening dashboard and an interactive patient report interface with cited recommendations, verification results, and raw EHR comparison. DIASENTINEL demonstrates a practical framework for reliable, auditable, and privacy-preserving LLM-based clinical decision support.

Xiaoyu Tao, Mingyue Cheng, Ze Guo, Bokai Pan, Qi Liu, Shijin Wang

Real-world time-series forecasting is rarely a one-shot model invocation: practitioners must formulate tasks, connect data and models, incorporate domain expertise, assess prediction plausibility, and communicate uncerta…

入选理由：multi-agent / agentic system / autonomous agent

查看 arXiv 摘要

Real-world time-series forecasting is rarely a one-shot model invocation: practitioners must formulate tasks, connect data and models, incorporate domain expertise, assess prediction plausibility, and communicate uncertainty. Specialized forecasting models provide strong numerical predictions but usually operate in fixed pipelines, while general-purpose large language model (LLM) agents often lack forecasting-specific checks, constraints, and stopping rules. We present CastClaw, a human-in-the-loop autonomous forecasting system built through forecasting-oriented harness engineering. CastClaw connects data, specialized models, analytical tools, user input, and a versioned execution record in one runtime. Users specify the target, horizon, constraints, and hypotheses in natural language. Starting from a supplied or model-generated forecast, CastClaw checks temporal patterns and user constraints; when evidence is missing, it retrieves context, runs an analysis or another model, or asks the user. It then keeps, revises, or escalates the result under explicit stopping conditions. The output contains the final forecast and an execution report recording inputs, evidence, actions, and revisions. In this five-dataset electricity-price setting, CastClaw reports the lowest point-estimate MSE and MAE among 16 baselines. A Nord Pool case demonstrates the inspectable workflow. CastClaw was also validated offline on provincial electricity-load data from North China covering January--June 2026.

HSRM: Hidden-State Reward Models for Test-Time Verification

Xianzhi Li, Xiaodan Zhu

HSRM：基于隐藏状态的轻量级推理验证模型

入选理由：利用隐藏状态验证推理，轻量高效替代文本重读验证

查看 arXiv 摘要

Large language models can often generate plausible mathematical reasoning traces, but reliably identifying the correct solution among multiple candidates remains a key challenge. Existing test-time reasoning pipelines typically rely on text-based verifiers that re-read each generated solution, making verification an expensive component of inference. Prior work has shown, however, that LLMs often encode correctness-related signals in their internal representations, including awareness of when their own answers are likely to be wrong. Building on this observation, we introduce HSRM, a lightweight hidden-state reward model that verifies candidate solutions by directly reading the generator's internal representations rather than re-processing its text. HSRM extracts hidden states from a frozen generator at reasoning-step boundaries and uses a small Transformer encoder to rank candidates. It is trained from self-generated trajectories with outcome labels, requiring neither human-written process supervision nor a large pretrained verifier. Across four mathematical reasoning benchmarks, HSRM matches or outperforms a 55M-parameter text-only energy verifier in 15 of 16 generator--dataset settings while using only about 2M parameters, providing an efficient alternative to text-only verification by reusing representations already computed during generation.

BAITBENCH: Measuring Agent Reward Hacking with Optional Shortcuts Planted in ML Tasks

Pradyumna Shyama Prasad, Meiri Anto, Leon Eshuijs, Julian Moncarz, Kaustubh Kislay, Juan J. Vazquez

BAITBENCH：测量代理在ML任务中的奖励作弊行为

入选理由：首个专测数据/任务内奖励作弊的基准BAITBENCH

查看 arXiv 摘要

LLM agents are increasingly used to run autonomous ML experiments, iterating on target metrics with little human oversight. Prior work has documented reward hacking in these environments, bringing into question the validity of produced research and the broader safety case for AI R&D. Existing benchmarks do not measure exploits that live in the data or the modeling task itself. We introduce BAITBENCH, a suite of three synthetic tabular ML tasks that each contain a shortcut that allows agents to inflate the public test score but fail on a hidden test set. Since the shortcut is optional and using it breaks no stated rule, BAITBENCH measures how often models exploit the shortcut to achieve inflated scores. Across seven frontier agents scored by our two-stage judge pipeline, 57.1% of runs exhibit reward hacking, with five of seven above 50%. Agents cheat even under a second condition where they are prompted not to -the mean cheating rate remains above 50%. We release BAITBENCH, along with the judge implementation, and an annotated dataset of transcripts containing reward hacks as a testbed for evaluating reward-hacking mitigations head-to-head.

Context-Aware Interleaved Batching for WhisperX

Carlos Bain, Max Bain

While WhisperX accelerates speech transcription via intra-audio batching, it isolates audio segments, losing the historical context needed for coherent punctuation and terminology transcription. Conversely, standard Whisper retains context sequentially but suffers from slow inference and hallucination loops. To achieve the best of both worlds, we propose Context-Aware Interleaved Batching. By using VAD-derived segment boundaries, our algorithm stabilizes Whisper's text conditioning, allowing us to safely maintain continuous historical context across batched audio segments. As demonstrated on long-form audio benchmarks, this approach reduces Word Error Rate (WER) and improves proper noun transcription, all while maintaining high-throughput inference speeds.

LISynSeg: Data-Centric Label-to-Image Synthesis for Cross-Modality Whole-Heart Segmentation

Jiacheng Wang, Ivana Isgum, Ipek Oguz

Whole-heart segmentation (WHS) in computed tomography (CT) and magnetic resonance imaging (MRI) is affected by acquisition shifts and heterogeneous cardiac annotations. Existing WHS systems combine architectural design,…

入选理由：daily-corpus novelty; cross-category; empirical/release signal

查看 arXiv 摘要

Whole-heart segmentation (WHS) in computed tomography (CT) and magnetic resonance imaging (MRI) is affected by acquisition shifts and heterogeneous cardiac annotations. Existing WHS systems combine architectural design, transfer learning, and generic spatial or intensity augmentation. We investigate whether changes to data augmentation and training supervision can improve cross-modality WHS while the segmentation architecture is held constant. We present LISynSeg, a data-centric approach that augments real-image nnU-Net training with label-to-image synthesis. Synthetic volumes are generated from cardiac label maps using contrast and acquisition perturbations calibrated to the training cohort, then mixed with real images to retain thoracic context absent from the labels (and thus the synthesized images). We model cardiac label variation through controlled changes in myocardial wall thickness and partial supervision of uncertain vessel endpoints. On the CARE Whole-Heart benchmark, synthetic-only training performs worse than the real-image nnU-Net baseline, whereas calibrated real-synthetic training improves cross-modality segmentation without changing the architecture; the improvement is larger for MRI than for CT. The results show that modifying the training data strategy can benefit model development for heterogeneous cardiac data. Code and trained weights will be released at https://github.com/MedICL-VU/Care26_LISynSeg.

🔥 CyberForge CVE of the Day #039 🚨 CVE-2026-77956 — AshAi EEx Template Evaluation Enables Conditional Remote Code Execution A newly disclosed AshAi vulnerability turns attacker-controlled prompt content into executable Elixir code inside the host application. And here is the crucial distinction: this is not ordinary LLM prompt injection. The malicious text can execute on the server before the prompt ever reaches the model. No jailbreak, cooperative model, valid provider API key or successful LLM response is required. 🔑 Key details: ⭐ Current severity: High — CVSS v4.0: 8.9 ⭐ Additional score: Critical — CVSS v3.1: 9.8 🧠 Weakness: CWE-94 — Improper Control of Generation of Code 🎯 Target: ash-project AshAi / Hex package ash_ai 🧩 Component: AshAi.Actions.Prompt 🔓 Authentication: None in the vendor’s exposed example; consuming apps may impose their own controls 👆 User interaction: None ⚙️ Complexity: Low, with Attack Requirements Present under CVSS v4 ⚔️ Impact: Conditional remote code execution 🛡️ Affected: ash_ai >=0.1.0 and <1.0.0 ✅ Fixed: AshAi 1.0.0 🧪 Public PoC: Yes — complete reproduction in the official vendor advisory 🌍 Active exploitation: None confirmed as of 1 September 2026 📋 CISA KEV: Not listed 📊 CISA SSVC: PoC / Not automatable / Total technical impact 📉 EPSS: 0.38% at review time 🧬 What actually went wrong? AshAi prompt actions support several configuration styles. One documented form is a runtime function that builds a prompt or list of messages from the action input and execution context. That is a perfectly natural place for an application developer to use values from input.arguments. In vulnerable AshAi releases, prompt content returned by this runtime function can pass through EEx.eval_string/2. EEx is Elixir’s embedded template engine, so content the developer intended to be ordinary LLM message text can be interpreted again as Elixir source. If attacker-controlled request data is copied into that returned content, the trust boundary collapses: 1️⃣ An attacker reaches an exposed AshAi prompt action. 2️⃣ Their request value becomes part of the runtime-generated prompt. 3️⃣ Vulnerable AshAi treats that prompt content as an EEx template. 4️⃣ Attacker-supplied EEx expressions execute inside the application’s BEAM process. 5️⃣ Only after that does the application attempt to contact the configured model provider. The vendor’s official demonstration proves the ordering beautifully: the code-execution marker fires even though the later prompt action fails because no OpenAI API key is configured. The LLM never needs to process the malicious prompt. 🤖 Prompt injection versus code injection: Ordinary prompt injection attempts to manipulate a model’s instructions, tools or output. CVE-2026-77956 instead makes the application server compile text as Elixir. The model is not the execution engine—the vulnerable BEAM application is. That means system prompts, model alignment, output filtering and provider-side abuse controls do not fix the root cause. This belongs firmly in the server-side code-injection and RCE world. ⚠️ Exploitability is conditional: Merely finding AshAi 0.x in a dependency list does not prove that a service is remotely exploitable. The complete path requires: ✅ An affected AshAi version below 1.0.0 ✅ A prompt action using the runtime function form ✅ Attacker-controlled request/action data placed into the function’s returned prompt content ✅ An HTTP, GraphQL, JSON, MCP or other untrusted interface capable of invoking that action If the consuming application requires authentication, the attacker must satisfy that application-level control. In an exposed unauthenticated route like the vendor’s example, no account or special privileges are needed. There is also no universal vulnerable URL or parameter. The /analyze route and text field shown in the official PoC belong to the demonstration application, not AshAi itself. 📊 The scoring wrinkle: Current vendor and CNA metadata use: CVSS:4.0/AV/AC/AT/PR/UI/VC/VI/VA/SC/SI/SA — 8.9 High The Local metric models the vulnerable library being invoked inside its consuming application, while Attack Requirements Present acknowledges that the app must use and expose the dangerous runtime pattern. In practical deployments, the malicious input can still arrive remotely through an application endpoint. NVD-linked CVSS v3.1 enrichment captures that path as 9.8 Critical with Network reachability. The public CVE record initially carried a CVSS v4.0 10.0 Network/AT vector before being revised on 31 August to the current 8.9 Local/AT assessment. The revised score does not erase the demonstrated RCE; it more carefully represents the required application configuration. 💥 Potential impact: Successful exploitation runs Elixir with the privileges of the Ash application process. Depending on the deployment, an attacker could potentially: 🔹 Read application secrets and environment variables 🔹 Access model-provider or database credentials 🔹 Query business data available to the service 🔹 Read or modify application files 🔹 Reach internal services permitted by network policy 🔹 Launch operating-system commands or additional tooling 🔹 Establish persistence or move laterally where surrounding controls allow it This does not automatically grant root access, container escape, Kubernetes administration or full cloud-account compromise. The blast radius depends on service permissions, secret scoping, filesystem controls and network segmentation. 🛠️ How version 1.0.0 fixes it: The patch separates trusted static prompt templates from runtime-generated content. 🔹 Static developer-authored templates can still use EEx as intended. 🔹 Content returned by a runtime prompt function is normalised with EEx evaluation disabled. 🔹 The change covers strings, system/user tuples and message lists. 🔹 A regression test verifies that EEx-shaped runtime text remains inert message content instead of executing. That is the correct trust model: static application configuration may be a template, but the result of a runtime function must remain data. 🔎 Defender hunting guide: 1️⃣ Inventory - Search mix.lock, SBOMs, containers and deployed Elixir releases for ash_ai below 1.0.0. Check every web node and worker—not merely the version requested in mix.exs. 2️⃣ Review application code - Look for AshAi.Actions.Prompt, prompt: fn, prompt functions using input.arguments, and returned strings or messages assembled from request-derived values. 3️⃣ Map exposure - Identify every API, GraphQL operation, MCP surface, background job or internal interface able to invoke those actions. Record its authentication and authorisation controls. 4️⃣ Hunt request telemetry - Search action inputs and proxy logs for EEx delimiters such as <% and <%=, including encoded forms. Treat these as hunting clues rather than complete signatures—encoding and alternate Elixir constructs can bypass simple matching. 5️⃣ Correlate workload behaviour - Investigate unusual EEx compilation errors, action failures before any provider call, new outbound connections, suspicious file writes and unexpected child processes launched by beam.smp or the Elixir release. The absence of OpenAI, Anthropic or other provider logs does not prove safety. The vulnerable evaluation occurs first. 🛡️ Defensive action: ✅ Upgrade to AshAi 1.0.0 or later ✅ Refresh and verify the resolved lockfile ✅ Test integrations because 1.0.0 is a major release ✅ Rebuild containers and Elixir release artefacts ✅ Redeploy every web and worker node ✅ Disable exposed vulnerable prompt actions until patched ✅ Apply strong authentication and explicit action-level authorisation ✅ Run the BEAM service as a non-root, least-privileged identity ✅ Restrict filesystem writes and unnecessary outbound access ✅ Scope database, cloud and model-provider credentials tightly If exploitation is suspected, isolate and rebuild the workload from a trusted fixed image, preserve application/EDR/network evidence, rotate every credential accessible to the service and inspect internal systems contacted by it. Do not rely on blocking EEx markers as the permanent fix. It is a brittle filter around a code-evaluation flaw; upgrading is the remediation. 🧪 Exploitation status: The official vendor advisory contains a complete reviewed PoC, so exploitability is not theoretical. However, public PoC availability is not the same as active exploitation. No confirmed in-the-wild attacks were identified during CyberForge research, and the CVE was not present in CISA’s KEV catalog on 1 September 2026. The early EPSS probability of 0.38% is low, but the record is exceptionally young and the vendor PoC is already public. EPSS should inform prioritisation—not overrule exposure, technical impact or first-party evidence. 🔥 CyberForge verdict: CVE-2026-77956 is a superb example of why every interpretation boundary matters in AI-enabled applications. A developer believes they are constructing text for a model. The library silently interprets that runtime text as a program. Once an untrusted request crosses that boundary, the model becomes irrelevant and the host application is exposed. This is not universal “install AshAi and get remotely owned” RCE. It requires a vulnerable runtime prompt pattern and an attacker-reachable action. But where that chain exists, server-side execution happens before the provider call and without model credentials or victim interaction. Internet-facing AshAi 0.x deployments deserve urgent inventory, upgrade and threat hunting.
